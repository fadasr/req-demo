The three views

A claim is an obligation with a stable id and a content-addressed meaning. Everything else is a view over it.

  • The V-modelThe layer map: needs → system → software → architecture → code, with tests and ISO safety.
  • Component overlayreq's own arch_overlay.py: each component colored by the worst satisfaction outcome.
  • Coverage matrixEvery claim, its design/code elements, its linked tests and its derived requirements.
  • Spec projectionreq render: the human-readable selection, regenerated, never hand-edited.

What the gate says

UNVERIFIABLE no signed Baseline, and 121 claims have no linked test. The projections are current.

FAIL with both JUnit reports, nine ADAS claims are linked to three failing SYS.5 cases.

The policy is not “green at any cost”: “we could not tell” and “a test failed” are different answers.

How it is made

  1. Import the pinned export with --links --tests --areas: 362 needs in, 135 claims out, 8 named skips, 219 not selected by type.
  2. Author: 39 claims remain unstructured; the ADAS pass is done. Pins hold where a bound is load-bearing.
  3. Link: 220 claim relations, 56 req-satisfies links to architecture/components/code, 16 JUnit links.
  4. Gate: req check runs both variants, both projections and completeness; req gate --test-report judges the evidence.
  5. Render: the graph and this site are regenerated from the JSON views, never edited by hand.
